# 로컬 AI 뉴스 시스템 구현 명세와 완료 계획

기준일: 2026-09-28. 이 문서는 현재 저장소의 **실제 구현**, **비공개 실행 결과**, **아직 필요한 개발**을 한곳에서 이어 읽기 위한 작업 명세다. 설계 배경은 [시스템 설계](LOCAL_AI_NEWS_SYSTEM.md), 출처별 상세 규칙은 [수집·파싱 명세](SOURCE_ACQUISITION_SPEC.md), 명령과 실행 기록은 [런북](LOCAL_AI_NEWS_RUNBOOK.md), 누적 작업 이력은 [구현 계획](LOCAL_AI_NEWS_IMPLEMENTATION_PLAN.md)에 둔다. 2026-09-29에 고정한 [일일 반복 수집·편집·발행 구현 명세](DAILY_NEWS_INGESTION_IMPLEMENTATION.md)는 이 문서의 E단계 조정기를 실제 출처·상태·시험 단위로 풀어 쓴다. 이 문서의 수치와 판정은 기준일의 스냅샷이며 운영 발행 완료를 뜻하지 않는다.

최신 전체 비공개 사이트 사본은 [22절](#22-abb-dunia-고객-사례-승인과-전체-서비스의-남은-연결), 그 뒤의 후보 장부 연결은 [23절](#23-읽었지만-새-사건이-아닌-자료의-비공개-판정-계약)을 읽는다. 사본은 승인 기사 27개·영향 과거 회차 13개·지식 노트 18개·생성 파일 284개(HTML 258개)·digest 132개이며 기존 RSS 40개 GUID/발행 시각을 보존했다. ABB 고객 사례를 원문부터 직접 검토해 9월 3일 과거 회차에 추가한 **로컬 사본**이고 Drive·실제 공개·08시 실행기와 구분한다.

## 1. 만들 결과와 절대 유지할 조건

하나의 오전 8시 실행에서 국내외 8개 분야의 기술·제품과 기업 동향을 조사하고, 산업용·협동로봇 제조사, 기업 IR·공시, 논문, 대학·연구실 창업을 함께 추적한다. 공개 결과는 사건을 바로 이해할 수 있는 육하원칙 기사, 충분한 근거가 있는 경우에만 실리는 심층 분석, 전문용어의 정의·원리·관련 사건·변화 이력이다. 뉴스·브리핑은 카드·내용이 있는 탭·`#` 태그로 읽고, 연결지도는 별도 화면에서만 제공한다.

발견한 URL이나 모델 초안은 기사가 아니다. 원문 bytes와 발표일·본문·숫자 조건을 확인한 뒤, 근거 있는 문장만 승인한다. 회사의 계획/주장과 실행/외부 검증, 논문의 초록과 전문, 공동저자/자문/기술이전/공동창업을 분리한다. 근거가 약한 해석, 빈 분석, 취재·검증·시스템 안내 문구는 공개 원고에서 생략한다.

Google Drive `Projects / Tech Knowledge`의 `Editions`, `Knowledge`, `Signals`, `TrendTopics`가 작성 원본의 최종 보관 위치다. `vault/`는 편집·생성 사본, `.local/research/local-ai/`는 원문 bytes·실패·모델 원출력·판정 이유를 보존하는 비공개 작업 공간이다. 웹, RSS, GitHub digest는 **같은 승인 입력**에서 생성한다. 기존 08:00 KST 예약 하나를 사용하고 유료 API·중복 예약·로봇만의 대체 브리핑은 추가하지 않는다.

CLI `research.mjs`의 한 run은 `--run` ID, 입력 fingerprint, 단계 journal, 파일 SHA로 고정한다. `collect`와 `reparse`는 새 관측과 새 파싱을 구분한다. `select-source`는 이미 저장된 여러 원문에서 exact URL을 골라 별도 run에 고정하고, `bundle`은 서로 다른 독립 근거를 새 네트워크 요청 없이 묶는다. 입력이 바뀌면 기존 승인/원문 run을 수정하지 않고 새 ID로 생성한다. 동일 입력 재시작은 중복 원문·기사·발행을 만들지 않아야 한다.

## 4. 데이터 식별자·날짜·상태

| 객체           | 키와 필수 연결                                                           | 날짜/상태와 검증 규칙                                                     |
| -------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| 발견 후보      | 후보 URL, 발견 채널/언어, 원발표·전재 계보                               | `discovered_at`; 후보 수는 기사 수가 아님                                 |
| 수집 관측      | 요청 URL, 최종 URL, HTTP/정책/네트워크 결과                              | `observed_at`; 실패 뒤 성공은 새 관측으로 추가                            |
| 원문 판본      | `source_id`, 원 bytes SHA-256, `source_version_id`, 실제 원문 경로       | 같은 bytes 판본은 불변; 공식 정정·본문 변경은 새 판본                     |
| 파싱 판본      | source version, parser/profile fingerprint, `parse_id`, block/page/표 ID | 제목·발표일 근거의 0개/복수/충돌은 자동 확정 금지                         |
| 사실 후보      | claim ID, 문자 그대로의 인용, block ID, 숫자 단위·분모·조건·회사 귀속    | 구조 검사와 `unreviewed`/verified/deferred/rejected 판정 분리             |
| 사건 기사      | 기존 `event_id`, 원 발표일, 회차, 검토일, 출처·전문용어 ID               | 제목/원문 URL 수정에도 기존 URL·RSS GUID 유지; 과거 정정은 신규 사건 아님 |
| 지식·변화 이력 | 용어/회사/연구 ID, 근거 claim·event, 관계 이유                           | 사건 날짜와 검토 날짜를 따로 저장; 공동 등장만으로 관계 생성 금지         |

원문 발표일, 실행/시행일, 수집 관측일, 회차 발행일, 재검토일은 서로 다른 시간이다. 연도만 표시된 목록, PDF 생성일, 관련 기사 날짜, 시간대 없는 문자열은 정밀한 원문 발표 시각으로 자동 승격하지 않는다. 검토 상태 `unreviewed`·`verified`·`excluded`와 접근 실패/보류를 구분한다. `excluded`를 결정하면 내용을 비공개로 보존하고 공개 주소에는 본문을 재노출하지 않는 상태 페이지를 두며 뉴스 목록·검색·RSS·digest·용어 이력·지도에서 모두 제거한다.

## 5. 원문별 구현 방법과 수용 사례

출처 등록은 숫자를 늘리는 작업이 아니다. 한 경로를 사용 가능하다고 판정하려면 **목록 시작→기간 또는 cursor 종료→상세 원문 bytes→날짜/본문/첨부→중복·정정·실패 재개**를 실제 자료로 시험한다. 자료 유형별 도입 순서는 다음과 같다.

| 원문 유형        | 먼저 구현·확인할 입력                                        | 파서에서 보존할 정보                                     | 수용 실패 사례                                                   |
| ---------------- | ------------------------------------------------------------ | -------------------------------------------------------- | ---------------------------------------------------------------- |
| RSS/Atom         | 피드 URL, GUID/permalink, ETag/Last-Modified, 삭제/수정 항목 | 피드 문장은 발견 후보; 상세 기사 원문과 발표일 별도 확보 | 깨진 XML, 같은 GUID 수정, 상세 403, 빈 피드와 접근 실패 구분     |
| 정적 뉴스룸      | 현지어 목록의 연도/날짜·다음 페이지·상세 URL                 | 기사 제목·본문·게시/수정일, 첨부·사양표·캡션             | 내비게이션/관련 기사 혼입, 날짜 0개/복수, 목록만 성공            |
| 동적 목록/API    | 화면이 실제 호출한 허용 JSON 또는 공식 API, 페이지 cursor    | 페이지 원본과 상세 별도 bytes, 종료 근거, 중복 항목      | endpoint 변경, 누락 페이지, 로그인/robots 차단, 타임아웃 뒤 재개 |
| IR·공시          | 기업/법인 ID, 보고 기간, 제출/정정 ID와 첨부                 | 목표·계획/집행/실적, 돈의 통화·단위·기간, 표 각주        | 모회사/자회사 혼동, 투자계획을 집행 실적으로 표기, 정정 누락     |
| 논문·학회        | DOI/arXiv/학회 ID, 초록·정식 원문 판본                       | 방법·비교 대상·표본·실험 조건·한계, PDF 페이지/표/그림   | 초록을 전문 분석으로 격상, preprint와 최종판 중복, 수식 OCR 오독 |

안전한 취득은 robots와 이용 조건을 확인하고 공개 요청만 사용한다. URL·DNS/IP·리다이렉트 정책, 응답 크기/시간/동시 요청 한도, 조건부 요청을 공통 수집기에 둔다. 차단·403·429·503·다운로드 손상은 모두 별도 receipt다. 공식 HTML/PDF가 대체로 확보되어도 최초 실패 기록을 삭제하지 않는다. PDF는 텍스트/표/페이지/좌표를 먼저 읽고 네이티브 텍스트가 없는 페이지만 OCR 후보로 만든다. OCR 숫자·수식은 원형과 직접 대조한다. 수집기는 원 bytes를 저장하고 파서는 네트워크 없이 그 bytes만 읽는다.

**현재 실제 사례.** FANUC 영문 목록과 HD 공식 뉴스 목록은 2026-09-01부터 2026-09-28 전까지의 기간을 순회했다. 기존 9월 13일 FANUC AI Welding Agent 기사에 대해 일본어 원문 22블록과 영어 공식판 23블록을 별도 저장·묶고, 로컬 추출 후보 6개 중 과장·인용 불일치 2개를 보류한 뒤 직접 읽은 사실 4개를 추가했다(최종 검증 8개). 제품명만으로는 일반 `AI Agents` 메커니즘을 입증하지 못해 기존 용어 링크와 회차 메타데이터를 제거했다.

HD–에이딘 사건은 9월 11일 당시 두 보도를 저장했고 뉴스핌 exact profile로 AI 자동 요약·기자 이메일을 제외해 본문 6블록과 기사 시각 `2026-09-11T10:23:07+09:00`을 다시 파싱했다. 이데일리 본문은 7블록이다. 모델 후보의 숫자 조건 3개를 원문 표현대로 교정하고 공동 개발 계획 1개를 직접 추가해 최종 6개 사실을 검증했다. **130억 원 지분 취득·160억 원 전체 투자 유치·연 3만 대 생산체제 목표는 서로 다른 범위와 상태**로 쓴다. 9월 14일 HD 공식 글은 뒤에 나온 보강 근거이지 9월 13일의 당시 출처가 아니다. OpenAI Habitat 원 URL은 다시 요청해도 HTTP 403으로, 접근 보류 상태다.

## 6. 모델·추론 수준과 원고 품질

현재 운영 후보는 무료 로컬 Ollama의 [`model-execution-policy/v1`](../data/research-model-policy.json)이며 다섯 역할의 시작 모델을 `qwen3.8:27b`로 고정했다. `search_plan`, `fact_extract`, `article_write`, `concept_write`는 `think:false`; 길거나 상충하는 증거 비교 후보인 `evidence_compare`만 `think:medium`이다. 공통 context 16,384·최대 출력 4,096 토큰, 추출 입력 20,000자/배치 최대 6사실/전체 900초다. 실제 모델·digest·Ollama 버전·prompt/profile·source SHA·지연/실패를 run에 저장한다. `medium` 설정은 비교 품질이 실증되었다는 뜻이 아니다.

모델은 질의 후보, 인용이 달린 주장 후보, 한국어 초안, 비교 후보를 만든다. 프로그램은 JSON 구조·인용 문자열의 실제 존재·숫자/단위/날짜 형식을 검사한다. **의미**, 주체·행위·계획과 완료·성과의 귀속, 비교 조건, 원문이 말하지 않은 인과는 사람이 확인한다. 검토자는 직접 읽은 원문 블록에서 후보 누락을 추가하거나 잘못된 후보를 보류/거부하고, 정정한 한국어 원고만 승인한다. 심층 분석은 기업 목표→자원 배분→변화→실제 성과, 논문 문제→방법→비교 조건→적용 범위, 연구 사업화 연구→확인된 창업 관계→제품/고객/투자 순서를 검토하되 근거 없는 절은 만들지 않는다.

정식 모델 선택은 서로 다른 실물 40개 개발·20개 잠금 보류 자료로 결정한다. 분야·국내외·언어·원문 유형·장문/표/수식·회사 주장/독립 자료를 층화한다. 두 모델 또는 `think:false`/`medium`을 **같은 원문, 같은 작업, 같은 사람 기준 답안**에서 비교한다. 핵심 사건 누락, 사실·숫자·날짜·시제·귀속 오류, 불필요한 추론, 한국어 독서 품질, 총 실행시간·메모리·타임아웃/재개를 평가한다. 사람이 바로잡은 기존 기사를 잠금 보류 정답으로 재사용하지 않는다. 기준 미달이면 기사 발행을 막고 검토형 운영을 유지한다. 더 큰 모델 도입은 이 측정 결과와 장비 예산으로만 결정한다.

## 7. 독자 원고·키워드·누적 지식의 변환

일반 기사 한 건의 공개 순서는 **제목 → 원 발표일 → 분야/테마/기업·제품 `#` 태그 → 2~4문장 육하원칙 리드 → 필요한 사실 설명 → 원문**이다. 리드에는 누가 무엇을 언제·어디서 했는지와 규모·방법/배경을 자연스럽게 담되 모든 항목을 억지로 채우지 않는다. 원문에 없는 이유는 쓰지 않는다. 상세 설명은 장식적인 “왜 중요한가” 반복 대신 제품 범위, 계약/금액의 성격, 실험 조건, 실제 적용 단계에 쓴다. 주요 소식 3~5개와 내용이 있는 분야 탭을 생성하고 심층 분석이 승인된 날에만 해당 탭을 만든다. RSS·Markdown은 같은 원고를 순차 제목으로 직렬화한다.

전문용어는 별도 정의와 작동 원리를 배워야 하는 정확한 기술 개념만 고정 ID로 등록한다. 일반 단어·기업·제품·기사 제목은 분류 태그이지 지도 노드가 아니다. 정확한 별칭 또는 명시적 기사 연결만 사용하고, 공동 등장만으로 개념 관계를 생성하지 않는다. 용어 페이지는 한 문장 정의, 원리, 혼동 개념, 승인 사건의 최신순 이력과 기사/원문 링크를 제공한다. 한 사건만 있으면 그 사건 하나를 보여 준다. 근거 있는 시간 비교가 없으면 변화 해설을 생략하고, 기사 수를 기술 성장이나 시장 성과로 해석하지 않는다. `Knowledge`, `Signals`, `TrendTopics`를 확장하며 중복 지식 저장소를 만들지 않는다.

과거 소급에서는 사건 ID·URL을 먼저 고정하고 원문 판본과 모든 등장 회차를 조사한다. 확인 결과는 최신 회차부터 작은 묶음으로 적용한다. 새 사실이 기존 판단을 보강/반박하면 사건 날짜와 **그 사실을 알게 된 검토 날짜**를 모두 남기고 과거 판단을 덮지 않는다. 기존 회차에서 빠진 별도 사건의 추가는 `historical_addition_review`로 원본 SHA·시간 경계·중복 여부를 검사한다. 과거 정정·추가는 오늘의 신규 RSS 항목으로 재발행하지 않는다.

## 9. 한 사건을 재개하는 실제 절차

1. `git status --short`와 기존 승인/Drive 기준·해당 사건의 모든 등장 위치를 확인한다. 원본 `vault/`와 이전 preview를 백업/해시로 보호한다.
2. 원문 URL·발표일·수정일·재인용 관계를 대조한다. 이미 저장한 source run은 `select-source`/`bundle`로 재사용하고, profile 수정만 필요한 경우 `reparse --run 새ID --source-run 기존ID`로 새 parse를 만든다. 성공/실패 관측을 섞어 이전 기록을 지우지 않는다.
3. `extract --run 새ID --source-run 고정ID --model-policy data/research-model-policy.json`는 모델 후보를 만든다. 후보가 중요한 내용을 빠뜨리면 원문 block의 정확한 짧은 인용을 `review.additions`로 추가한다. 검토 파일은 `--review`로 전달하되 .local에 두고 공개 저장소에 포함하지 않는다.
4. 원문을 직접 읽어 인용의 의미·주체·시점·숫자/단위/분모·조건·계획/완료를 표시한다. `draft` → 필요시 `correct` → `approve`는 각각 다른 산출물이며, 기사 ID/회차/원 발표일과 source SHA가 고정됐는지 재검사한다.
5. 기사에 의존한 용어 정의·관계·변화 이력·Signals/TrendTopics를 찾아 `note-review`한다. 참조만 남고 근거가 없어진 설명은 제거한다.
6. 기존 모든 승인 run과 새 run을 포함해 새 이름의 `preview`를 만들고 이전 preview와 변화 목록을 비교한다. 웹/RSS/GitHub에서 제목·리드·날짜·원문 URL을 대조한다. 승인/생성은 `vault/`·Drive·공개 서비스의 변경이 아니다.

## 18. 출처 한 경로를 반복 조사에 올리는 구체적 절차

### 18.1 등록과 시간창

1. `research-watchlist.json`의 `source_routes`에 기관/법인 ID, 공식 시작 URL, 언어, 기술·제품 또는 기업·운영 축, 자료 종류, 허용 host를 기록한다. 같은 발표의 번역판·보도자료 전재·고객 발표를 별도 사건으로 세지 않도록 `channel_id`와 출처 계보를 연결한다. `research-source-channels.json`의 기존 24개 발견 채널은 폭넓은 후보 탐색용이며 94개 등록 route의 완주 증거가 아니다.
2. `[since, until)`은 **발표 날짜의 반열린 기간**이다. 마지막 성공 cutoff, 겹치는 최근 7일 발견 구간, 이전 실패 backlog를 함께 조회한다. 오래된 중요 누락 사건은 당시 회차에 보완하며 오늘 기사로 날짜를 바꾸지 않는다. 목록에 정렬·페이지 구조가 없으면 완료 근거를 따로 설계하기 전까지 `incomplete`로 둔다.
3. 정적 목록은 `listing_profile`, 동적 공개 JSON/폼은 명시적인 `api_profile`, 상세 HTML/PDF는 `article_profiles[].url_pattern`과 본문/발표일 선택자로 구분한다. 현재 `scan-list` dispatch는 일반 한 페이지 HTML, HD, KUKA, ABB 경로만 인식한다. 다른 `api_profile`을 설정만 추가하면 `Unknown listing API profile`로 멈춘다.

### 18.2 수집과 파싱

1. `fetch.mjs`·`source-policy.mjs`가 robots/허용 host·DNS/IP/redirect·크기·시간 정책을 확인한 뒤 실제 요청/최종 URL/MIME/상태/관측 시각과 원 bytes SHA를 보존한다. 403/429/503, 로그인 HTML, 빈 본문, PDF 손상, 네트워크 중단을 서로 다른 관측으로 남긴다. 허용된 공식 대체 경로를 찾아도 실패 관측을 삭제하지 않는다.
2. `archive.mjs`와 `run-state.mjs`는 source version과 `--run`의 입력 fingerprint/단계 journal을 보존한다. 같은 bytes를 새 선택자로 다시 읽을 때는 `reparse --run <새ID> --source-run <기존ID>`를 사용한다. 다시 받은 bytes와 저장 bytes를 혼동하지 않고, 원문 변경은 새 source version으로, 선택자 변경은 새 parse로 식별한다.
3. `integrations/research-worker/worker.py`는 저장 파일만 읽어 제목·발표일·본문·인용문·표·그림 설명/첨부를 block ID와 DOM/PDF page 위치로 낸다. 발행일 선택자가 0개 또는 여러 개, 본문이 기사 메뉴/관련 글뿐, 필요한 표/페이지가 빠진 경우는 자동 승인하지 않는다. PDF 생성 시각·HTTP Last-Modified·URL 날짜는 본문 발표일을 대신하지 않는다. 네이티브 텍스트가 없는 페이지의 OCR은 후보로만 기록한다.
4. 목록에서 날짜가 실제로 오래된 항목에 도달했거나 총건수·마지막 페이지를 검사했고, 기간 내 **모든 선택 상세**의 bytes·본문·발표일을 확인했을 때만 `list-scan.json.status=window_scanned`로 둔다. 이 상태에서도 `candidates.json`은 `unreviewed`다. 상세 하나의 날짜 충돌/차단/파싱 실패, 페이지 수 변화, 예산 소진은 전체 창을 `incomplete`로 남기고 재개 지점을 보존한다.

### 18.4 RSS·공시·논문·교수 창업 경로의 같은 수용 기준

- RSS/Atom은 피드 GUID와 항목 수정 이력을 **발견 단서**로 쓰고 permalink의 상세 원문을 따로 수집한다. 피드가 비어도 요청 실패/부분 XML/정상 빈 피드를 구별한다.
- DART·SEC와 기업 IR은 법인/사업부 ID, 제출일·공개일·실제 시행일, 정정 번호, 첨부 PDF/표를 분리한다. 제출과 실적 기간을 같은 사건 날짜로 합치지 않는다.
- DOI/arXiv/학회 원문은 사전공개본과 정식 출판본의 식별자·판본을 연결하고, 초록만 확보했으면 전문 방법/한계의 심층 해설을 만들지 않는다. 표·수식·비교 조건을 원문 페이지에서 확인한다.
- 대학·연구실·TLO와 회사 자료는 동명이인과 역할을 각각 검증한다. 공동저자·기술자문·기술이전·공동창업은 별도 관계이며, 한 기관의 소개 문구만으로 제품 고객 도입이나 투자 완료를 단정하지 않는다.
- 모든 유형에서 고객/공급사/협회/지역·현지어 경로를 탐색하되 동일 회사 보도자료 전재를 독립적인 두 근거로 세지 않는다. 접근 실패는 조사 누락으로 이월하고 `새 소식 없음`으로 표시하지 않는다.

FANUC [날짜별 기타 공시자료](https://www.fanuc.co.jp/ja/ir/announce_other/)를 기술·제품 발표와 분리된 `기업·운영` 경로로 등록했다. 현재 registry는 24개 발견 채널·94개 등록 route·36개 기사 profile이다. 기존 뉴스 5경로에 이 공시 1경로를 더해 지정 기간의 목록과 상세를 검증한 route는 **6/94**다. `20260928-fanuc-ir-disclosures-sep-window-v2`는 `[2026-09-01, 2026-09-28)` 목록 PDF 링크 144개 중 창 안 2개를 수집했고, 목록 날짜와 PDF 첫 페이지의 9월 18일·3일 날짜가 일치했다. 둘 다 미검토 후보다. `window_scanned`는 링크/상세 수집 계약의 통과이며 기업 전략 판단이나 발행 승인이 아니다.

구현은 `data/research-watchlist.json`의 FANUC route, `data/research-acquisition.json`의 `single-page` 목록 rule과 두 PDF만의 exact profile을 사용한다. 새 scanner나 유료 API는 도입하지 않았다. 목록은 연도/일자 제목의 조합을 링크 날짜로 읽고, PDF는 1쪽의 제목·날짜와 페이지별 본문을 남긴다. 자세한 선택자·실패 조건·실제 원문 수는 [출처 명세 31절](SOURCE_ACQUISITION_SPEC.md#31-fanuc-날짜별-기타-공시자료의-목록pdf-경로), 재현 명령과 저장 run은 [런북 61절](LOCAL_AI_NEWS_RUNBOOK.md#61-fanuc-날짜별-ir-공시의-원문-수집과-재현)을 따른다.

다음 개발에서는 두 PDF의 결의/취득 기간·수량·금액·계획 대비 실행·법인/표 각주를 사람이 읽어 claim으로 고정한다. 기사가 필요하면 기존 사건 inventory와 대조해 당시 회차로만 편입한다. 새 공시가 다른 서식이면 별도 exact profile과 정상·실패 fixture를 추가한다. 날짜가 명확하지 않은 FANUC 분기 결산 목록은 별도 공개일 증거와 종료 규칙이 필요하다. 이어 다른 제조사 IR·DART/SEC·논문·대학/TLO를 같은 단계로 확장하되 각 유형의 법인/연구자·시제·판본 계약을 따로 검사한다. 이 우선순위와 전체 B~F 수용 조건은 [구현 계획 19.37절](LOCAL_AI_NEWS_IMPLEMENTATION_PLAN.md#1937-fanuc-공시-기간-수집-이후의-편집과-자료-확장)에 연결했다.

## 22. ABB Dunia 고객 사례 승인과 전체 서비스의 남은 연결

ABB Robotics의 고객 사례 URL은 기존 Robotics feed 구간 완주에서 확보한 원 HTML의 **한 항목**이다. 인용문 포함 parse 17블록을 선택하고 로컬 Qwen3.8 27B/`fact_extract`가 낸 6개 후보를 사람이 원문에 대조했다. 모델은 현재 GoFa 셀과 고체/액체 투입·분산 작업을 빠뜨렸다. 원문 exact block에 묶어 세 사실을 추가하고, ABB가 전한 **한 실험의 20회 결과**와 Dunia의 **순차 방식 200회 초과 추정**을 서로 다른 사실로 처리했다. 후자와 제목의 `up to 10x`는 공개 원고에서 사용하지 않았다. 모델 원고의 분야/테마와 현재·계획 혼합을 교정한 승인 사건은 `368b46197845ce07`이다([원문·블록 계약](SOURCE_ACQUISITION_SPEC.md#32-abb-고객-사례의-게시-시각현재-작업추정-성능-분리), [명령과 결과](LOCAL_AI_NEWS_RUNBOOK.md#63-abb-dunia-고객-사례의-직접-검토와-비공개-소급)).

ABB HTML의 `scheduledPublishDate`는 UTC 2026-09-02 13:13:50.623이고 `Published` 상태다. KST 9월 2일 22:13:50으로 기존 9월 3일 회차의 수집 시간에 들어가며 원본 회차 SHA와 URL 중복을 검토했다. 이 메타데이터의 의미는 ABB가 기록한 게시 예정 시각까지다. 고객 실험실의 설치일이나 독립 관측한 최초 공개 시각을 나타내지 않는다. 이 판단을 `historical_addition_review`에 남기고 원본 `vault/`를 건드리지 않았다. 새 사건을 9월 28일 신규 회차에 넣지 않았다.

현재 통합 사본 `20260928-abb-dunia-historical-private-site-v1`은 승인 run **27**, 영향 회차 **13**, 지식 노트 **18**, 생성 public **284/HTML 258**, digest **132**이다. 새 기사·9월 3일 브리핑·RSS·digest의 제목/리드/ABB 원문이 일치하고 기존 RSS **40개 `(GUID,pubDate)`가 그대로**다. 로컬 Chromium 1440/390px의 기사/브리핑 4화면, 출처 링크, 지도 부재, 가로 넘침 0, page error 0, 분야 탭 URL과 뒤로 가기를 확인했다. 이 검사는 `preview-manifest.json`의 `candidate_published:false`, `drive_verified:false`, `browser_verified:false`를 운영 완료로 바꾸지 않는다.

다음 납품 순서는 [계획 19.39절](LOCAL_AI_NEWS_IMPLEMENTATION_PLAN.md#1939-abb-고객-사례-소급-이후의-구현과-완료-순서)의 B1/B2/C1/C2/D/E/F 표를 따른다. B1의 ABB 현대화 특집은 **신규 사건이 없는 배경 자료**로 직접 판정해 공개 항목을 만들지 않았다([런북 63.1절](LOCAL_AI_NEWS_RUNBOOK.md#631-abb-현대화-특집의-배경-자료-판정)). 남은 (1) 92개 구형 회차/801구간과 의존 지식의 전수 판정, (2) 국내외 제조사·IR/공시·논문·대학/TLO의 route별 기간 종료·원문 수집, (3) 독립 40개 개발/20개 잠금 모델 평가, (4) 기존 08시 단일 조정기와 Drive 원격 bytes/부모/revision readback, (5) 실제 웹·RSS·GitHub 확인 및 서로 다른 신규 성공 7회가 서로 다른 완료 증거를 요구한다. **어느 한 단계의 성공도 다음 단계의 승인으로 전이하지 않는다.**

## 23. 읽었지만 새 사건이 아닌 자료의 비공개 판정 계약

### 23.1 구분과 입력

공식 원문을 읽어도 새 제품·계약·고객 설치·투자 집행·측정 성과의 발표가 없을 수 있다. 이것은 **기존 공개 기사를 삭제하는 `excluded` 검토**와 구별한다. `candidate-disposition`은 발견 단계의 후보 한 건을 비공개 `rejected`로 종결할 때만 사용한다. 로컬 모델 점수·제목·매체 분류만으로 이 상태를 만들지 않는다. 원문이 막혔거나 날짜·본문이 불명확하면 `deferred`로 남긴다.

입력은 (1) `--candidate-run`의 원래 `candidates.json`/저장 원문, (2) `--source-run`의 검토에 사용한 저장 원문/parse, (3) `.local/research/local-ai/` 안의 `editorial-candidate-disposition/v1` 검토 JSON, (4) 현재 작성 `vault/Editions`의 기사·원문 URL이다. 기본적으로 후보와 검토 run을 같은 것으로 본다. 원문은 같지만 인용문·표를 보강해 **다시 파싱한 경우** `--candidate-run`과 `--source-run`을 분리한다. 두 run의 `source_version_id`가 같아야 하고 `parse_id`는 달라도 된다. ABB 실제 사례의 최초 parse `09fbb289...`와 검토 parse `eddb2961...`이 이 경로를 검증했다.

### 23.2 원자적 갱신과 상태

[`selectStoredSources`](../scripts/research/parser.mjs)가 각 run의 원문 bytes SHA, 원본 URL ID, 불변 parse artifact와 블록 해시를 확인한다. 검토 JSON의 source ID/version/body SHA/parse ID, 원 발표일과 parse 날짜, 관측 이후 검토일, 인용 블록, 직접 읽음 표시, 네 사건성 항목의 명시적 `false`, 공개 채널 여섯 개의 `false`를 검사한다. 후보가 원래 run에 정확히 하나 있고 같은 날짜·URL을 가리키는지도 검사한다. 기존 작성 회차의 동일 URL, 검증 완료 후보, 고정 사건 ID, 여러 후보가 같은 URL에 결합된 경우에는 갱신을 거부한다.

후보 장부 lock 아래에서 **그 후보만** `review_status: rejected`, 비공개 `reason`, 원문·parse·검토 경로와 검토 JSON SHA로 갱신한다. 새 후보라면 한 건만 추가한다. 별도 run lock과 `research-candidate-disposition/v1` 영수증이 같은 입력의 재실행을 고정한다. [`mergeBacklog`](../scripts/research/discovery.mjs)는 이후 동일 URL을 발견해도 판정과 최초 사건 시각을 덮지 않는다. [`researchWindow`](../scripts/research-window.mjs)는 `rejected`를 `resolved/closed`로 취급한다. 작성 vault, 승인 기사 run, 웹·RSS·digest·지식 연결은 이 명령의 쓰기 대상이 아니다.

### 23.3 실패·재검토·완료 범위

검토 JSON과 저장 원문 bytes의 불일치, 근거 블록 부재, 후보 run과 검토 run의 다른 원문 version, 날짜 불일치, 기존 기사 충돌은 **장부 쓰기 전에 실패**한다. 같은 run ID로 다른 검토 JSON을 넣으면 실패하고 새 run ID가 필요하다. 기존 `rejected` 후보에 다른 판정을 조용히 덮지 않는다. 이후 **상세 기사에서 추출한 내용**이 달라지면 판정을 이력으로 보존한 채 `deferred`로 다시 올린다. 다시 읽어 판정할 때는 새 근거·검토 JSON·run ID가 필요하며, 재개만으로 기사가 발행되지는 않는다. 목록 HTML 판본 변경이나 상세 HTML의 본문 밖 장식 변경만으로는 재개하지 않는다. 상세 계약은 [24절](#24-기사-본문-변경에-따른-후보-재검토-계약)을 따른다.

실제 ABB 현대화 특집 적용으로 사전 55건 → 56건(검증 42·보류 13·종결 1)이 됐고 기존 후보 원본 및 공개 자료는 불변이다. 같은 명령의 두 번째 실행에서 장부 바이트 SHA가 그대로다. 새 테스트는 손상된 bytes·가짜 블록·기존 기사 URL·검증 후보 거부와 후보/근거 run 분리를 재현한다([런북 64절](LOCAL_AI_NEWS_RUNBOOK.md#64-배경-자료-판정의-후보-장부-기록)). 이것은 B1의 **후보 처리**만 완료한 증거이며, B2 전체 소급·C 출처 확장·D 독립 품질·E 08시/Drive·F 실제 배포/7회 완료 증거가 아니다.

## 24. 기사 본문 변경에 따른 후보 재검토 계약

### 24.1 두 판본과 한 후보의 역할

`source_version_id`는 저장한 **원본 bytes**의 식별자다. HTML의 탐색 메뉴·추적 코드·페이지 장식만 바뀌어도 달라진다. [`articleContentFingerprint`](../scripts/research/parser.mjs)는 `status: extracted`인 parse의 제목, `dates.published_at`, **순서가 있는 본문 block text 전체**를 JSON으로 직렬화한 SHA-256이다. parse ID, 관측 시각, DOM 위치, 원본의 다른 HTML은 이 지문에 넣지 않는다. 지문은 편집기가 실제로 읽은 추출 내용의 동등성 검사이며 원본 bytes 보관·원문 재검증을 대체하지 않는다. 추출기가 본문을 빠뜨리면 그 누락 부분의 변화도 감지하지 못하므로 출처별 exact profile·필수 필드·원문 검토가 계속 필요하다.

`scan-list --merge-backlog`은 목록 날짜 창을 검사하고 상세 원문을 저장·파싱한 뒤에만 후보를 장부에 합친다. 후보는 `article_source_version_id`, `article_parse_id`, `article_observed_at`, `article_content_sha256`를 갖는다. 발견 목록의 version은 `discovery[]`에 따로 남긴다. 기존 후보의 고정 key/URL, 최초 발견일, 검증된 사건 ID와 편집 제목은 병합 때 보존한다. 동일 입력 반복은 장부 bytes를 바꾸지 않는다.

### 24.2 상태 전이와 비교 실패

| 입력 비교                                              | 비공개 후보 장부 결과                                                                                   |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| 목록 HTML만 변경                                       | `discovery[]` 근거만 추가하고 `rejected` 유지                                                           |
| 상세 원본 bytes 변경, 제목·발표일·본문 block text 동일 | 최근 원본 version/관측 시각을 기록하고 `rejected` 유지                                                  |
| 상세의 추출 제목·발표일·본문 중 하나 변경              | 기존 판정·검토 해시를 `disposition_history[]`로 옮기고 `deferred`/`source_revision_alert`로 재검토 요청 |
| 같은 관측 시각에 서로 다른 추출 내용                   | 어느 관측이 최신인지 정할 수 없어 병합 실패                                                             |
| 새 후보에 본문 지문이 없거나 과거 종결에 지문이 없음   | 이전 원본 version과 새 version이 다르면 보수적으로 재검토; 기존 판정은 지워지지 않음                    |
| 더 오래된 관측이 늦게 병합됨                           | 최신 기사 version·내용·검토 상태를 과거 값으로 되돌리지 않음                                            |

지문이 없는 옛 종결에서 같은 원본을 다른 parse ID로 다시 추출했을 때는 이전 검토에서 빠진 인용문·본문이 잡혔을 수 있으므로 `deferred`로 올린다. `source_revision_alert`는 변경 기준(`content`·`raw_source`·`parse_version`), 이전/현재 원본 version, 이전/현재 내용 지문, 감지 시각을 **비공개**로 기록한다. 원문 내용 변경을 확인해도 뉴스성이 생겼다고 추론하지 않는다. `researchWindow`의 `pending/historical-review`가 새 검토 대상으로 보일 뿐이다. 새 원문을 직접 읽고 출처 version·parse·발표일·블록·기존 공개 기사 충돌을 확인한 뒤 `candidate-disposition`으로 다시 배경 자료라고 판정할 수 있다. 새 사건이라면 일반 사실 검토→기사 승인 경로를 따른다. 원문이 차단됐거나 parse가 불완전하면 `deferred`를 유지한다.

기존 ABB 판정처럼 지문 도입 전에 만들어진 비공개 `rejected` 기록은 **같은 검토 JSON과 같은 `candidate-disposition` run**의 재실행으로 원 저장 parse에서 지문을 계산해 채울 수 있다. 판정·영수증·최초 source version·원본 후보 파일은 유지한다. 앞서 다른 내용의 상세 원문을 이미 관측했다면 이 보강을 거부한다. 운영 장부를 통째로 예전 백업으로 덮어쓰지 말고 변경 전 bytes를 별도 비공개 복구본에 보존한다.

### 24.3 검증·운영 경계

관련 회귀는 `research-source-selection`, `research-list-scan`, `research-runtime`, `research-candidate-disposition`, `research-api-scan`, `research-abb-scan`, `research-kuka-scan` 테스트다. 실제 KUKA 독일어 두 기사의 서로 다른 네 HTML 판본은 각 기사에서 동일한 추출 내용 지문을 냈고, 동일 `scan-list --merge-backlog` 재실행은 `changed:false`였다([런북 65절](LOCAL_AI_NEWS_RUNBOOK.md#65-후보-재발견과-기사-내용-지문의-실제-검증)). 두 KUKA 후보는 아직 `unreviewed`이며 이 시험이 직접 사실 검토나 기사 승인을 수행한 것은 아니다. 작성 `vault/`, Drive, 웹·RSS·GitHub, 오전 8시 실행은 변경하지 않았다.

## 25. 다국어 원문의 기존 사건 연결 계약

### 25.1 해결하는 중복과 입력의 권위

목록에서 새 URL이 발견됐다는 사실과 새 **사건**이라는 결론은 다르다. 같은 제조사의 독문·영문 공식 발표를 URL 문자 패턴이나 모델 이름만으로 합치면 두 날짜의 제품 업데이트도 잘못 합칠 수 있다. [`candidate-identity.mjs`](../scripts/research/candidate-identity.mjs)의 `candidate-identity` 명령은 이미 `vault/Editions`에 검증 기사로 존재하는 **고정 사건 ID**에, 다른 언어판의 미검토 후보 **한 건**을 사람이 명시적으로 연결한다. `research.mjs`가 현재 Editions의 `extractArticles`에서 `event_id`, 기사 제목, 원 발표일, 검토 상태, 출처 URL을 새로 읽는다. 검토 JSON에 적은 대상 ID만 믿거나 `vault/News` 생성 파일을 원본으로 삼지 않는다.

입력은 (1) 새 언어판의 `source-run`에 보존된 실제 HTML bytes와 parse, (2) 기존 기사 원문의 별도 `published-source-run` bytes와 parse, (3) 새 후보가 나온 `candidate-run`의 `candidates.json`, (4) 사람이 직접 쓴 **비공개** `review` JSON, (5) 현재 candidate-backlog다. 첫째와 셋째는 같은 source version이어야 하지만 다른 parse ID는 허용한다. 두 발표의 명시된 `published_at` 날짜는 같아야 한다. 기존 기사는 `verified`여야 하고 검토 JSON의 제목·원문 URL·날짜가 실제 원고와 같아야 한다. 이는 영문 기사의 현재 원고까지 재검증했다는 보증이 아니라 **동일 사건 ID를 붙일 대상**의 무결성 검사다.

### 25.2 검토 JSON과 저장 결과

`editorial-candidate-identity/v1`에는 `decision:same_published_event`, 검토자·검토일, `candidate`와 `published` 각각의 원 URL/source ID/source version/body SHA/parse ID/원 발표일, 기존 `event_id`/기사 제목을 기록한다. `matches[]`는 최소 `identity_marker`와 `event_action`을 각각 갖고 양쪽의 `block_id`, 정확히 포함된 짧은 원문 excerpt, 사람이 쓴 비교 결론을 요구한다. 발표일과 제품·고객·논문 등 정체성, 실제 행위와 상태, 중요한 수치·예정 일정을 함께 읽는다. 확인한 것만 `same_event_reason`에 적는다. `new_article:false`·`candidate_published:false`는 이 명령이 신규 발행을 하지 않는다는 명시적 계약이다.

명령은 저장 원문 bytes SHA와 불변 parse artifact를 다시 확인하고, 인용 excerpt가 두 parse 블록에 **실제로 포함**되는지 검사한다. 인용의 **의미가 동등한지**는 검토자의 책임이며 단순 문자열 검사가 번역을 승인하지 않는다. 후보 장부에서는 기존 `key`, 최초 발견, URL, 발견 경로를 그대로 두고 `review_status:verified`, 기존 `event_id`, 최신 기사 내용 지문, `identity`의 두 run·원문 version·검토 해시를 저장한다. 별도 `runs/<run>/candidate-identity.json`은 입력 판본과 결과 ID를 고정한다. 같은 입력 재실행은 장부 bytes를 바꾸지 않으며 원래 `candidates.json`과 공개 기사/피드/지식에는 쓰지 않는다. 근거가 바뀌면 기존 영수증을 덮지 않고 새 run ID로 검토한다.

### 25.3 실패·변경 상태표

| 관측 또는 오류                                                                             | 처리                                                                                                                       |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 원 bytes/parse 손상, 인용 블록 또는 excerpt 부재                                           | 장부 쓰기 전 실패. 원본과 profile을 고쳐 새 run으로 재검토                                                                 |
| 두 원 발표일 불일치, 대상 기사 ID/제목/URL/날짜 불일치, 후보 URL이 다른 사건에 이미 연결됨 | 자동 병합 금지. 사건 계보와 원고를 수동 대조                                                                               |
| 후보 원본이 최근 관측한 기사 내용 지문과 다름                                              | 오래된 근거로 현재 후보를 검증하지 않음. 최신 상세를 저장·재검토                                                           |
| 동일 HTML wrapper 변경, 추출 제목·게시일·본문은 동일                                       | 저장 source version/관측만 갱신하고 기존 동일 사건 연결 유지                                                               |
| 연결된 언어판의 추출 제목·게시일·본문 변경                                                 | 이전 `identity`를 `identity_history[]`에 보존, 같은 사건 ID는 유지하되 `deferred`/`source_revision_alert`로 변경 판정 대기 |
| 위 변경 후보가 이미 발행 사건 ID와 연결됨                                                  | `researchWindow`의 `pending`에서 `review-source-revision`으로 표시. 새 기사로 자동 발행하지 않음                           |
| 새 원문이 여전히 같은 사건이라고 직접 재확인                                               | 최신 source/parse/블록을 인용한 **새** 검토 run으로 `verified` 복귀, 이전 연결 이력 유지                                   |

다른 사건으로 갈라진 경우에는 근거 없이 예전 ID를 새 기사에 재사용하지 않는다. 기존 출처와 원고의 수정·제외 여부, 과거 회차/의존 지식을 별도 편집 절차에서 판단한다. `source_revision_alert`와 판단 이유는 독자 페이지, RSS, digest에 투영하지 않는다. 구체적인 실제 적용은 [현재 빌드 25절](LOCAL_AI_NEWS_CURRENT_BUILD.md#25-kuka-독일어-재게시와-기존-사건의-명시적-연결), 재현 명령은 [런북 66절](LOCAL_AI_NEWS_RUNBOOK.md#66-kuka-다국어-동일-사건의-근거-연결)을 따른다.

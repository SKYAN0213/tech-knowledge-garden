# 육하원칙과 매일 심층 분석

2026-09-14 이후 새 원고에 `editorial_format: six-w/v1`을 사용한다. 이 문서가 과거 기사 카드의 핵심/의미/확인할 점 및 무엇이 바뀌었나/왜 중요한가 요구를 대체한다. 원고의 10개 대분류와 기존 분야·테마는 유지한다. 과거 기사에는 소급하지 않는다.

## 매일 조사

출처와 언어 확장은 `SOURCE_DIVERSITY.md`를 함께 따른다. context의 추가 탐색 경로와 7일·30일 출처 분포를 보고 특정 블로그에 집중되기 전에 부족한 분야·지역·출처 종류를 조사한다. 고정 기업 목록 외에도 산업 전문지·고객·부품사·시스템 통합사·공시·협회·연구실에서 사건을 발견하고 개별 원문으로 확인한다.

`npm run context`의 watchlist, editorial, 기존 주제·원문을 먼저 읽는다. `data/research-watchlist.json`에는 8개 분야마다 국내 2곳·해외 2곳 기업, 국내 8곳·해외 8곳 대학·기관을 등록한다. 같은 기업은 한 번 수집한다. 명단 밖 중요 사건도 탐색한다. 등록된 주소는 탐색 시작점이며 사건의 근거는 개별 발표 permalink다. 접근 확인은 내용 검토를 뜻하지 않는다.

Research에는 분야 × 기술·제품/기업·운영 × 국내/해외 32행을 기록한다. 각 행에 실제 확인 URL, 확인 시각, 원문 발표 시각과 근거, 선정/제외 사유, 접근 실패를 남긴다. 확인·부분 확인·접근 실패·미실시를 구분한다. 국내외 동일한 조사 기회를 배분하되 기사 비율을 강제하지 않는다. 고정 기업의 IR/공시와 대학 연구/기술이전 경로를 독립 확인하며 모든 기관을 정밀 조사했다고 추정하지 않는다.

월 첫 실제 실행에서 명단을 검토한다. 신규 기업은 분야의 직접 관련 사업, 일차 자료 접근성, 기존 명단과의 차별성을 기준으로 선정한다. 대학은 연구와 기술이전 공개 경로 및 8개 분야의 전체 포괄성을 확인한다. 변경 사유와 확인 시각을 Research에 남기고 명단의 `review_month`를 갱신한다. 관련성은 GPT 검토이며 홈페이지 응답으로 증명되지 않는다.

## 기사와 근거 메타데이터

제목 다음에 기존 다섯 분류 필드를 쓰고, 2~4문장의 리드를 쓴다. 누가 무엇을 했는지 먼저 전달하고 언제·어디서·어떻게·왜를 자연스럽게 포함한다. 배경 미공개는 미공개로 기록한다. 날짜·수치는 단위와 비교 기준을 붙인다. 육하원칙 항목 이름은 독자에게 반복 노출하지 않는다. 소제목은 해당 기사의 구체적인 사실을 전달한다.

원고 frontmatter의 `article_records`는 기사 제목과 정확히 일치하는 레코드 배열이다. 각 레코드는 다음 필드를 갖는다.

- `title`, `kind`(사건 뉴스/기업 전략/논문 해설/연구 사업화), `region`(국내/해외/국제 공동).
- `lead`: 본문에 그대로 실린 2~4문장, 최대 900자. 웹·GitHub·RSS가 동일 문장을 사용한다.
- `facts`: who/when/where/what/how/why 각각 근거 확인 내용. 미공개는 명시하되 사실을 만들지 않는다. 발표일과 시행일, 회사 주장과 확인 사실을 구분한다.
- `papers`: 없으면 []. 논문별 `work_id`(검토 후 재사용하는 영문 고정 ID), `identifiers`(doi:… 또는 arxiv:…), `access`(초록/전문), `status`(사전공개/동료심사), `evidence_url`(기사 Source List 원문).
- `relations`: 없으면 []. 각각 person_id, person_name, affiliation, organization, role, claim, as_of, evidence_urls. 역할은 공동저자/기술자문/기술이전/공동창업/창업/소속이다. 창업·공동창업은 대학과 회사의 서로 다른 원문 최소 2개로 확인한다. 동명이인은 소속·연구 주제·공식 소개를 대조한다.
- `topic_ids`: 관련 누적 주제 ID 배열. 심층은 최소 1개. `analysis_summary`, `next_check`는 심층 필수다.

논문의 사전공개·정식 출판은 내용과 저자·공식 연결을 검토한 뒤 같은 work_id에 식별자를 추가한다. 제목 유사도만으로 합치지 않는다. 새로운 사건의 URL ID는 유지하므로 후속 출판 소식과 논문 자체의 동일성은 별개다. 현재 소속을 과거 소속으로 덮어쓰지 않는다.

원고의 `headlines`에는 실제 기사 제목 3~5개를 편집 순서대로 적는다. 기사가 3개 미만이면 모두, 빈 회차면 []다. 심층을 생략하면 `deep_skip_reason`에 근거 부족·접근 제한 등 실제 사유를 적는다. 사유는 취재용이며 RSS를 운영 안내로 채우지 않는다.

## 하루 심층 1건

context의 `next_deep_kind`에 따라 기업 전략 → 논문 해설 → 연구 사업화 순환을 기본으로 한다. 중대한 새 발표로 순서를 바꾸면 Research에 이유를 기록한다. 충분한 근거가 없으면 생략한다. 심층도 전체 40건·분야당 5건 안에 포함한다. 동일 사건을 일반 기사와 심층 기사로 두 번 작성하지 않는다.

- 기업 전략: 밝힌 목표 → 투자·인력·계약 집행 → 이전 전략과 차이 → 성과와 불확실성. IR·사업보고서·실적 발표·투자자 설명회와 실제 실행 자료를 비교한다. 계획과 집행, 전사와 부문 실적을 구분한다.
- 논문 해설: 문제 → 방법 → 비교 조건과 결과 → 한계와 적용 범위. 전문을 읽은 논문만 심층으로 쓴다. 사전공개와 동료심사를 구분하고 실험 성능을 상용 제품 성능으로 표현하지 않는다.
- 연구 사업화: 연구·교수 → 명시적 창업/기술이전 관계 → 제품·고객·투자 → 다음 확인 단계. 교수 자문을 창업으로 표현하지 않는다.

분석 문단은 `분석`으로 명시하며 관련 주장마다 원문 근거를 제공한다. 수치·인과·전략의 사실 검증은 GPT의 원문 검토가 담당하며 형식 검사 통과로 대체되지 않는다.

## 누적 기록과 배포

기업 전략은 `company-<기업 ID>`, 연구 주제는 `research-<주제 ID>`, 사업화는 `venture-<회사 ID>`를 기본 누적 주제 ID로 쓴다. 실제 검토 질문이 있는 경우에만 기존 TrendTopics 형식으로 생성한다. 새 topic은 원고 저장 후 context를 호출하기 전에 먼저 만든다. context에서 event_id를 얻은 다음 최신 판단·반대 조건·다음 확인을 쓰고 같은 회차 Signals에 해당 event_id와 topic_id 관측을 남긴다. 과거 관측을 삭제하지 않는다. 최초 과거 기준 자료는 새 사건으로 싣지 않고 분석 배경으로 출처를 밝힌다.

새 논문 식별자와 인물 관계는 News 메타데이터 및 context에 보존한다. 전문용어 그래프에는 자동 추가하지 않는다. 심층 기사에서 누적 주제로 연결하며 기존 주제 웹·GitHub 이력에서 과거 기사와 원문을 따라갈 수 있다.

주요 소식 → 분야별 기사 → 오늘의 심층 분석 순서로 웹·GitHub·RSS에 전달한다. 뉴스와 브리핑에 지도를 넣지 않는다. 기존 8시 예약과 Drive 4개 원본 폴더·보관·배포 순서를 유지한다. 추가 유료 API나 예약을 만들지 않는다.

## 첫 7회 운영 점검

각 실제 실행의 공개 결과 확인 뒤 `.local/research/runs/<회차>.json`에 `edition`, `checked_at`, `drive_verified`, `deployment_verified`, `rss_verified`, `github_verified`, `coverage`(32행: sector/channel/region/status/urls), `deep_kind` 또는 `skip_reason`, `reading_minutes`, `notes`를 기록한다. 접근 실패는 urls: []로 기록할 수 있으나 사유를 notes에 남긴다. 체크한 URL을 성공으로 자동 간주하지 않는다.

`node scripts/research-audit.mjs`는 모든 배포 검증이 완료된 서로 다른 회차만 집계한다. 첫 7회에 대해 국내외 조사 상태, 미확인 범위, 심층 종류/생략, 분량을 출력한다. GPT가 실제 원문을 재검토해 반복 기사·편중·근거 품질을 평가하고 Research에 저장한다. 실행 누락과 설정 변경을 완료 횟수로 세지 않는다. Research와 감사 출력은 기존 개인 Drive Research 보관에 포함하며 공개 저장소에 커밋하지 않는다.

## 독자 화면과 편집 기록 분리

뉴스·브리핑·RSS·공유 Markdown에는 시스템 안내문을 넣지 않는다. 작업 완료, 샘플 여부, 취재 범위·누락, 검증 절차, 저장·배포 상태, cutoff, 사용법 등 운영 문구는 `.local/` 취재·검증 기록과 작업 보고에만 남긴다. 기사에는 실제 발표일, 출처, 계획/완료 구분, 회사 주장과 분석 표시, 기사에 실제 인용한 수치의 성능 조건을 유지한다. 과거 자료는 시장 배경으로 구분하여 당일 새 소식처럼 보이지 않게 한다.

웹에서는 짧은 주요 소식 뒤에 분야별 선택 탭과 심층 분석을 구분한다. 기존 8개 분야 및 추가 로봇 시장 조사는 유지한다. 탭은 키보드와 모바일에서 사용할 수 있어야 하며 JavaScript가 없어도 기사에 접근할 수 있어야 한다. RSS·Markdown은 같은 내용을 순차 제목 구조로 제공한다. 기사 날짜 아래에 분야·테마·기업 등 확인된 태그를 `#태그` 블록으로 표시한다. 클릭 기능이 없는 태그는 버튼처럼 동작하는 것으로 표시하지 않는다. 태그가 지식지도 노드를 자동 생성하지 않는다.

## 근거 있는 분석만 게재

분석은 원문과 확인된 비교 자료로 뒷받침되고 독자에게 구체적인 정보를 더할 때만 쓴다. 서로 다른 제품 발표를 묶어 업계 방향·성과·인과관계로 확대 해석하지 않는다. 근거가 부족하면 해당 추론과 분석 섹션 자체를 생략한다. “분석할 수 없다”, “초기 관찰이다”, “확인되지 않았다”, “별도 자료가 필요하다” 같은 분석 능력·취재 부족에 대한 해명이나 빈 분석 안내를 독자 본문에 쓰지 않는다. 생략 이유와 후속 조사 질문은 비공개 취재 기록에만 남긴다. 이 규칙은 앞선 심층 구성 지침보다 우선하며 심층 분량을 채우기 위해 분석을 만들지 않는다.

발표일·예정 일정·회사에 귀속된 주장 및 실제 인용한 수치의 실험 조건은 사실의 일부로 정확하게 쓴다. 이를 생략해 계획을 완료로 바꾸거나 주장을 검증된 성과로 보이게 하지 않는다. 본문에 제시하지 않은 성과·수치를 가정한 뒤 반박하거나 경고하는 문장은 쓰지 않는다. 게재할 분석이 없으면 분석 탭도 표시하지 않는다.

## 소급 재검토와 고정 기사 주소

2026-09-13 사용자 승인으로 과거 기사도 원문 재확인 후 수정한다. 이전의 소급 금지 문구보다 이 규칙이 우선한다. 원문 주소의 해시로 생성된 기존 ID는 최초 전환 시 `article_reviews`에 고정한다. 각 기록은 기사 제목과 일치하는 `title`, 16자리 `event_id`, `review_status`(unreviewed/verified/excluded), `concept_ids` 배열을 갖는다. verified에는 실제 원문 `published_at`과 `reviewed_at` 날짜(YYYY-MM-DD)를 기록한다. 원문 재확인 전에는 verified로 바꾸지 않는다. 기사 제목·출처 수정 시 같은 event_id를 사용한다.

검증한 기사만 명시적인 concept_ids로 용어 변화 이력의 근거가 된다. 기존 검색용 keywords나 이웃 용어의 공동 등장으로 이력을 생성하지 않는다. 같은 사건은 여러 회차에 있어도 한 번 검토하되 모든 등장 원고를 일치시킨다. article_reviews가 있는 회차의 분석 생략 이유와 후속 조사 질문은 `.local/retrospective/` 기록에 저장하며 원고에 강제하지 않는다.

제외한 사건의 원문·기존 본문·판정 이유는 비공개 Drive Research/Archive에 보관한다. 공개 Editions에 본문을 남겨둔 채 숨기지 않는다. 모든 공개 등장 원고에서 해당 기사와 사용하지 않는 출처를 제거하고 `excluded_events`에 ID만 남긴다. 생성기는 공개 본문에 제외 사건이 남아 있으면 실패한다. 기존 News 주소에는 비공개 상태만 표시하고 검색에는 등록하지 않는다. 연결된 Signals·TrendTopics·Knowledge의 근거도 함께 재검토한 뒤 발행한다. 구형 92회는 새 형식 추출기에 자동 포함되지 않으므로 별도 목록을 기준으로 누락 없이 검토한다.

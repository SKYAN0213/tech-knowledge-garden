# AWS가 설명한 AgentCore Memory 검색: 속성 조건으로 기억 후보를 먼저 좁힌다


AWS는 2026년 7월 2일(한국시간) Amazon Bedrock AgentCore Memory의 메타데이터 구성·기록·검색 방법을 설명하는 글을 공개했다. 이 서비스는 고객·개체별 네임스페이스 안에서 부서·우선순위·기간 같은 속성으로 기억 후보를 좁힌 뒤 벡터 유사도 검색을 수행한다. [원문 1](<https://aws.amazon.com/blogs/machine-learning/structured-memory-filtering-with-metadata-in-agentcore-memory/>)

### 검색 조건과 데이터 격리

네임스페이스는 고객·개체별 기억을 격리하는 기본 경계이고, 메타데이터 필터는 그 안의 데이터를 다시 분류한다. AWS는 tenant\_id 필터만으로 네임스페이스 격리를 대신하지 말라고 설명한다.

필터에 사용할 속성은 인덱스 키로 등록해야 한다. 대화에서 값을 추출해 기억 레코드에 채우려면 해당 키가 전략의 memoryRecordSchema에도 있어야 한다. 스키마에만 있는 비인덱스 속성은 읽을 수 있지만 필터에는 사용할 수 없다.

ListMemoryRecords는 유사도 검색 없이 속성 조건에 맞는 레코드 목록을 조회한다. 시스템 생성 시각과 갱신 시각인 x-amz-agentcore-memory-createdAt·x-amz-agentcore-memory-updatedAt에는 별도의 날짜 인덱스를 선언하지 않고 BEFORE·AFTER 조건을 사용할 수 있다. [원문 1](<https://aws.amazon.com/blogs/machine-learning/structured-memory-filtering-with-metadata-in-agentcore-memory/>)

### 값을 그대로 전달하는 추출과 직접 기록

애플리케이션이 이미 아는 값은 STRICTLY\_CONSISTENT로 지정하면 LLM이 다시 추론하지 않고 추출·통합 과정에 그대로 전달한다. 같은 결정적 속성 값을 가진 이벤트를 함께 추출하며, 값이 다른 레코드끼리는 통합하지 않는다.

AWS가 명시한 한도는 전략당 STRICTLY\_CONSISTENT 키 최대 3개다. 각각은 기억 리소스의 인덱스 키 10개 한도에서 한 자리를 차지하며, 추가한 인덱스 키는 제거할 수 없다.

BatchCreateMemoryRecords·BatchUpdateMemoryRecords는 추출을 거치지 않으므로 STRICTLY\_CONSISTENT 추출 설정이 적용되지 않는다. 직접 기록할 때 memoryStrategyId가 있으면 전략 스키마의 키만 저장하고 나머지는 버린다. 없으면 전달한 키를 그대로 저장하지만 필터에는 인덱스 키만 쓸 수 있다. [원문 1](<https://aws.amazon.com/blogs/machine-learning/structured-memory-filtering-with-metadata-in-agentcore-memory/>)

### 기존 기록과 평가 결과

인덱스 키는 추가 방식으로 확장한다. 새 키는 이후 이벤트와 기억 기록에 사용할 수 있지만 기존 기록에 자동으로 소급 추가되지는 않는다.

AWS는 여러 세션의 장기 대화를 다룬 LoCoMo 방식의 질문 151개로 평가했다고 밝혔다. 메타데이터 필터를 켰을 때 전체 질문의 답변 정확도는 40%에서 64%로 높아졌고, 기간·우선순위·부서 같은 문맥 경계에 의존하는 질문 부분집합에서는 16%에서 69%로 높아졌다고 보고했다. [원문 1](<https://aws.amazon.com/blogs/machine-learning/structured-memory-filtering-with-metadata-in-agentcore-memory/>)
